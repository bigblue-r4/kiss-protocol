Architecture Overview

How Gatekeeper, Fair Witness, and reporting components fit together

This overview describes the current Sentinel architecture at a functional level. It is meant to clarify how the system verifies activity, applies policy, preserves evidence, and supports later review.

Core flow

  1. An agent exchange or requested action occurs.
  2. Gatekeeper evaluates the event against explicit rules and trust boundaries.
  3. A decision is made: allow, hold, block, or escalate.
  4. Witness records are created with timestamps, source context, and supporting detail.
  5. Evidence is preserved for operator review, remediation, or reporting.

Components

1. Gatekeeper

The enforcement layer.

Gatekeeper sits at the trust boundary and monitors agent-to-agent or agent-to-tool activity. Its job is to:

  • inspect requests and outputs
  • apply explicit policy
  • pause or block high-risk actions
  • record the reason a rule was triggered

2. Fair Witness

The evidence and qualification layer.

Fair Witness records what was observed, where it came from, when it was seen, and what remains uncertain. This supports:

  • replayable review
  • qualified reporting
  • clearer separation of facts from interpretation
  • defensible audit trails

3. Telemetry and reporting

The operational layer.

Selected events are summarized into dashboards, incident records, and review packets. Public summaries stay limited; protected evidence remains sealed.

Example decision path

Stage Question Output
Observe What activity occurred? Timestamped event
Evaluate Which rule or trust boundary applies? Policy decision
Act Allow, hold, block, or escalate? Control action
Record What evidence should be retained? Witness entry / artifact link
Review What does the operator need to see next? Incident summary / remediation path

Design priorities

The architecture is optimized around five priorities:

  • verification — distinguish observed behavior from assumption
  • enforcement — intervene when a rule is crossed
  • evidence preservation — maintain usable records for later review
  • clarity — make system decisions understandable to operators and stakeholders
  • trust-material lifecycle control — support designs that reduce the persistence of compromised or stale trust artifacts over time

Current posture

Sentinel should be understood as a trust-and-safety control stack in active development. Some components are live, some are still in private alpha, and some remain in design or lab status. Public descriptions should stay aligned with what is actually deployed.
